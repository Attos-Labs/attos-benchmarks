# High-cardinality benchmark: Attos vs Go map vs Redis (10M, 50M, 100M keys)

Attos vs a native Go `map[string]string` vs Redis 7.0.15, on one dataset per size, 95% hit / 5% miss, one run per size. All numbers come from the raw logs in `results/` (the files named at the bottom of each per-size section); the tables are generated by `mkreport.py`. Reproduce with `N=<keys> WITH_REDIS=1 ./run.sh`.

## Test environment

- GCP `n2-highmem-8`: 8 vCPU Intel Xeon @ 2.80 GHz, 64 GB RAM, Ubuntu 24.04, kernel 7.0.0-1017-gcp, 100 GB pd-ssd, europe-west2-a (VM now deleted)
- Go 1.25.6, Redis 7.0.15 (jemalloc), attos-go `5a76278` (v2 format), single reader thread
- Keys: unique, 16–32 B (avg ≈24.0 B); values 8–32 B (avg ≈20.0 B); raw payload ≈44 B/key. Key counts: 10M, 50M, 100M
- Redis: private instance on a unix socket, no persistence, unpipelined GET (client round trip), 200k timed lookups (Attos/map: 3M)

**Reading it honestly:** at these sizes Attos holds roughly 2x less RAM than a Go map and 2.5x less than Redis (about 4.9 GB vs 9.7 GB vs 12.1 GB at 100M); the optional lean mode roughly halves Attos again. The RAM figure for Attos is file-backed mapped pages (shared, reclaimable page cache), not heap: the process heap stays ~1 MB. Lookups are 0.5–0.7 µs at P50 and 1–3.5 µs at P99.9, the fastest of the three, but the P99.9 advantage over the Go map shrinks with size (3.5 µs vs 4.5 µs at 100M) and Redis is 17–60 µs because it pays a network round trip. Cold start is the standout: ~0.1 ms at every size versus 4–59 s for rebuilding a map and 5–63 s for restarting Redis from RDB. "Zero GC pauses" is accurate in the sense that Attos allocates nothing per lookup and its heap is empty; under synthetic allocation churn the Attos process still sees GC cycles caused by that churn (the max-pause rows), so claim "no GC pressure from the dataset", not "no GC".

### Notes and caveats (read before quoting)

- *Attos lean-4B and LZ4 are optional compile modes that trade lookup speed for smaller files/RAM; lean stores a 4-byte key fingerprint, so a miss can in principle return a wrong hit (the `errors` row counts any).
- Cold start for Attos is measured with the file in the OS page cache (no root to drop caches); a first-ever read from a cold disk is slower.
- Attos RSS counts file-backed mapped pages that the process has touched; they are shared page cache and reclaimable, unlike heap. Both numbers are shown.
- The Go map is loaded from the same raw `kv.bin` file, pre-sized to N entries (the best case for the map).
- Redis latency includes a loopback round trip, so it is not a like-for-like in-process comparison; pipelining would change it.
- The churn phase is a synthetic allocator (64 KB every 0.25 ms; runs at least 20 s, so its lookup count exceeds the quiet phase) to expose GC interaction with a large live heap; real services differ.
